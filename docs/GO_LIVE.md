# التحويل من موقع العرض إلى موقع حقيقي

قرار صاحب المنتج (2026-11-06): الموقع المنشور https://madad-6p2.pages.dev يعمل الآن **بلا وضع العرض**، على نفس مشروع Supabase، لعرضه على لجنة التقييم. هذا يخالف SPEC §4/§16 (وضع العرض ومبدّل الأدوار) بموافقة صاحب المنتج، وهو مسجّل في `docs/DECISIONS.md`. كل قواعد CLAUDE.md وSPEC.md الأخرى سارية.

## ما تغيّر

| | قبل | بعد |
| --- | --- | --- |
| البناء (`.env.cloudflare`) | `VITE_DEMO=true` | `VITE_DEMO=false`: لا مبدّل أدوار، لا شارة «بيانات تجريبية»، لا زر «المتابعة بحساب المريض التجريبي» |
| البيانات | بذرة العرض (21 مؤسسة، 400 بلاغ، 1,500 بحث) | الكتالوج (40 دواء، 11 تصنيفًا) والإعدادات فقط. لا مؤسسات ولا بلاغات ولا عمليات بحث مصنوعة |
| الحسابات | 8 حسابات عرض بكلمة مرور معروفة | حُذفت كلها. بقيت الحسابات الحقيقية فقط |
| `demo_mode` | `true` | `false`، ودالة `demo_seed()` محذوفة |
| الباركود في الكتالوج | أرقام مختلقة (`6250000000001`…) | فارغ، حتى لا يطابق منتجًا غير موجود |

البذرة: `supabase/seed-live.sql`، تُولَّد بـ`npm run seed:live` من نفس ملفات JSON، ويتحقق CI من تطابقها. الدورة كاملة (عرض ← حقيقي ← عرض) مختبرة في `supabase/tests/live.test.ts`.

## النسخ الاحتياطية

1. **قاعدة البيانات:** نسخة كاملة قبل التحويل في المخطط الخاص `backup_demo_20261106`: كل جداول `public`، و`auth_users` و`auth_identities` و`storage_objects`. المخطط غير مكشوف للـAPI (مجرَّب: «Invalid schema»).
2. **الكود:** الوسم `demo-final-2026-11-06` على آخر نسخة بوضع العرض.

## الرجوع إلى موقع العرض

1. في Supabase ← SQL Editor: شغّل محتوى `supabase/seed.sql`. يعيد حسابات العرض والبيانات بأوقات حديثة ويفعّل `demo_mode`. الحسابات الحقيقية تبقى.
2. في `.env.cloudflare`: `VITE_DEMO=true`، ثم ارفع إلى `main`. ينشر Cloudflare تلقائيًا.

أما استرجاع لقطة 2026-11-06 حرفيًا من `backup_demo_20261106` فغير مطلوب عادة، لأن بذرة العرض تعيد كل شيء بأوقات حديثة (والأوقات القديمة ستظهر «غير مؤكد»). عند الاستغناء عن النسخة: `drop schema backup_demo_20261106 cascade;`

## حسابات فريق مدد

لا تُكتب كلمات مرور في أي ملف. الطريقة:

1. يسجّل كل عضو حسابه بنفسه من الموقع (بريد وكلمة مرور، أو Google).
2. تُرفع صلاحيته من SQL Editor:

```sql
update public.profiles set platform_role = 'super_admin'
where id = (select id from auth.users where email = '...');
-- أو 'reviewer' للمراجِع
```

بعدها يدير مدير النظام الأدوار من AD-09 (المستخدمون) مباشرة.

## قبل دخول اللجنة

- [ ] حسابا الفريق (مدير نظام + مراجِع) مسجّلان ومرفوعة صلاحيتهما.
- [ ] جُرّب السيناريو كاملًا مرة على الرابط: تسجيل مريض، تسجيل صيدلية (A-05)، اعتمادها (AD-02)، إضافة دواء وتحديثه (PH-04، PH-02)، وصول التنبيه.
- [ ] تسجيل الدخول بـGoogle في وضع الاختبار: لا يدخل إلا المستخدمون المضافون في Google Cloud. أضف من سيجرّب من اللجنة، أو اعتمد التسجيل بالبريد.
- [ ] أي صيدلية تُنشأ للعرض تحمل اسمًا يوضّح أنها للعرض، وتُعلَّق أو تُحذف بعده، حتى لا يذهب أحد إلى صيدلية غير موجودة.
- [ ] «تأكيد البريد» في Supabase (Authentication ← Providers ← Email): معطّل يعني تسجيلًا فوريًا مناسبًا للعرض؛ يُفضَّل تفعيله بعد العرض.

## ما لا يُفعل أبدًا

- لا `service_role` في أي ملف أمامي أو متغير بناء.
- لا تعطيل لـRLS، ولا تشغيل `seed.sql` على هذا المشروع إلا للرجوع المقصود إلى العرض.
- لا تعديل لـ`src/lib/freshness.ts` أو `displayOf`.
- لا تعديل لملفات `src/data/mock/seed/*.json` لأجل الموقع الحقيقي: هي تغذّي وضع mock والاختبارات.
